## 1. Executive Summary

Phase 2 builds upon the dynamic role-based login and registration foundation established in Phase 1 and the invitation system from Phase 2. This phase introduces an institutional multi-role registration, credential verification, and administrative approval workflow for MediConnect:

1. **Patient Portal (Direct Registration Preserved):** Public direct patient registration (`/register`) continues to operate without friction, granting immediate active login access (`approval_status = 'APPROVED'`, `is_active = True`).
2. **Doctor Credentialing & Approval:** Licensed medical practitioners submit institutional onboarding requests with NMC/State Medical Council registration numbers, council names, qualifications, experience, and designation. Requests are created in `PENDING_APPROVAL` status with login strictly blocked until approved by their target Hospital Super Admin.
3. **Hospital Front Desk / Receptionist Onboarding:** Front desk staff submit affiliation requests to a selected hospital (`PENDING_APPROVAL`), reviewed and approved by the target Hospital Super Admin.
4. **Hospital Super Admin & Branch Provisioning:** Prospective hospital administrators submit hospital credentialing requests with proposed hospital details (`hospital_id = None`, `PENDING_APPROVAL`). Only the Platform Owner can review and approve, which automatically provisions the hospital entity and grants administrative console access.
5. **Cross-Hospital IDOR Defense:** Strict tenant isolation ensures Hospital Super Admins can only review and approve/reject staff requests belonging to their own hospital institution.
6. **Indian Medical Council Alignment:** Demo doctors have been updated with realistic Indian medical qualifications, State Medical Council registration numbers (NMC, TSMC, DMC, KMC, MMC), and professional titles without changing genuine user credentials.

## 3. Backend Implementation Architecture

### 3.1 Model Enhancements (`backend/models.py`)
- Added fields, relationships, and helper methods to `User`:
  - `is_approved()`, `is_pending()`, `is_rejected()`
  - `approver` self-referential relationship (`approved_by_id`)
  - Updated `to_dict()` serialization to include `approval_status`, `approved_by_id`, `approved_at`, `rejection_reason`.
- Added `registration_number`, `council_name`, and `designation` to `Doctor` with serialization in `to_dict()`.

### 3.2 Defense-in-Depth Middleware (`backend/utils/auth_middleware.py`)
- **`jwt_required` & `roles_required`:**
  - Intercepts incoming JWT requests for users with `approval_status == 'PENDING_APPROVAL'` or `'REJECTED'`.
  - Blocks access to protected platform APIs with HTTP 403 Forbidden and structured payload (`error_code: 'ACCOUNT_PENDING_APPROVAL'`, `'ACCOUNT_REJECTED'`).
  - Added `approval_status` claim to JWT payload generated by `generate_token()`.

### 3.3 Public Registration Request API (`backend/routes/auth.py`)
- **`POST /api/auth/register-request`:**
  - Accepts `DOCTOR`, `RECEPTIONIST`, and `HOSPITAL_SUPER_ADMIN` registration payloads.
  - Strictly rejects `PLATFORM_OWNER` public registration attempts with HTTP 403 Forbidden.
  - Enforces password minimum length (&ge;6 chars) and confirm password matching.
  - Performs duplicate email checks (HTTP 409 Conflict) and duplicate NMC registration number checks (HTTP 409 Conflict).
  - Delegates `PATIENT` / `USER` role requests to standard `/api/auth/register` (instant active account).
  - Creates pending `User` with `approval_status = 'PENDING_APPROVAL'` and `is_active = False`.
  - For `DOCTOR`, creates a linked `Doctor` profile with status `'Pending'`.
- **`POST /api/auth/login` Interception:**
  - Before password authentication completes, verifies `approval_status`.
  - Pending accounts receive HTTP 403 with `error_code: 'ACCOUNT_PENDING_APPROVAL'`.
  - Rejected accounts receive HTTP 403 with `error_code: 'ACCOUNT_REJECTED'` and the specific `rejection_reason`.

### 3.4 Administrative Approval Management API (`backend/routes/approvals.py`)
- **Hospital Super Admin Endpoints:**
  - `GET /api/hospital/approvals?status=pending`: Lists pending registration requests scoped to caller's hospital.
  - `POST /api/hospital/approvals/<user_id>/approve`: Validates tenant scoping (`target.hospital_id == caller.hospital_id`), verifies role in (`DOCTOR`, `RECEPTIONIST`), activates user (`is_active = True`, `approval_status = 'APPROVED'`), activates Doctor profile (`status = 'Active'`), and logs audit entry.
  - `POST /api/hospital/approvals/<user_id>/reject`: Validates tenant scoping, records institutional rejection reason, marks user as `REJECTED`, and logs audit entry.
- **Platform Owner Endpoints:**
  - `GET /api/platform/approvals?status=pending`: Lists pending `HOSPITAL_SUPER_ADMIN` registration requests platform-wide.
  - `POST /api/platform/approvals/<user_id>/approve`: Automatically provisions the proposed Hospital entity with a unique URL slug, assigns the applicant to the newly created hospital, activates the applicant as `HOSPITAL_SUPER_ADMIN`, and logs audit entry.
  - `POST /api/platform/approvals/<user_id>/reject`: Rejects Super Admin onboarding request with recorded institutional justification.
- **Blueprint Registration:** Registered in `backend/app.py` under both `/api` and root URL prefixes.

### 3.5 Invitation Subsystem Synchronization (`backend/routes/invitations.py`)
- Synchronized `/api/invitations/accept` so newly created or linked accounts explicitly set `approval_status = 'APPROVED'`, `approved_by_id = invitation.invited_by_id`, and `approved_at = now_utc`, ensuring seamless coexistence between registration requests and direct invitations.
